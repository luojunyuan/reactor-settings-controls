# Reactor API Design

The source control is a WinUI `Control` with dependency properties, templates,
visual states, and `ItemsRepeater`. Reactor does not expose a mutable dependency
property surface for application controls. The equivalent architecture is a
typed declaration builder that lowers to the existing primitive declarations.

## Mapping

| SettingsControls | Reactor API |
| --- | --- |
| `Header`, `Description`, `Content` | `header`, `description`, `content` accepting `View` or text |
| `HeaderIcon`, `ActionIcon` | `header_icon`, `action_icon` accepting an icon view |
| `ContentAlignment` | Rust `ContentAlignment` enum |
| `IsClickEnabled`, `Click` | `is_click_enabled`, `on_click` |
| `IsActionIconVisible`, `ActionIconToolTip` | matching builder methods |
| `IsExpanded` | controlled `is_expanded` value |
| `Expanded`, `Collapsed` | `on_expanded`, `on_collapsed` |
| `Items`, `ItemsSource`, `ItemTemplate` | `items`, `items_iter`, `items_source_with`, `item_template` |
| `ItemsHeader`, `ItemsFooter` | matching content slots |
| `ItemContainerStyleSelector` | card builders carry their own item layout values |

## Composition rules

1. Each builder consumes itself and produces a `View`, so it can be used in
   `children`, `content`, component returns, and keyed relations.
2. String slots use Reactor's existing string-to-`TextBlock` conversion. A
   `SettingContent` wrapper is available when a caller wants an explicit slot
   value or to defer conversion.
3. Item collections use Reactor's `ItemsRepeater` and keyed declarations.
   `item` and `keyed_items` preserve application identity; positional helpers
   are intended for static lists.
4. Expansion is controlled state. A callback reports user changes, and the
   parent component owns the next `is_expanded` value, matching Reactor's
   controlled input pattern.
5. Click and expansion callbacks are Reactor callbacks, so they can be created
   with `ViewContext::callback`, `ComponentContext::message`, or ordinary
   closures without an event argument adapter.

The view tree deliberately uses only controls already generated by the checked
out `windows-rs` revision. This keeps reconciliation, event validation,
virtualization, and native realization inside windows-reactor instead of
introducing a second control runtime.
